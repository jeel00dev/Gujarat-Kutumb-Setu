# Research-backed implementation decisions

Research date: **20 September 2026**. The user reports approval of **Gujarat Kutumb Setu / ગુજરાત કુટુંબ સેતુ** and implementation work. This resolves the working product name for this repository; it does not supply government data-sharing credentials, an identity-service authorization, a production security certification, or an approved legal policy for every conditional SRS feature.

The two research baselines remain historical records. This implementation adds the **intended production-shaped frontend and a persistent local backend with simulated providers**, plus a statewide target design. It is not a separate throwaway demo UI: replacing an approved provider must preserve the resident/staff task flows. Never use real resident, Aadhaar, bank, certificate or health records in the local test environment.

## 1. What the requested NeGD precedent actually establishes

The [NeGD UP implementation record](https://negd.gov.in/isl/Directory/statedata/95), reopened for this implementation, describes secured state-data-centre hosting, separate verifiers/approvers, daily PDS synchronization, assisted access, staged department APIs, UP-specific Aadhaar permissions and a security audit. It reports **3.06 crore Family IDs, 12.63 crore mapped beneficiaries**, and **31+ departments / 73 schemes**. These are reported administrative figures, not independently reproduced benchmarks.

The technology list includes .NET, SQL Server, MQ and Power BI. The inspected record supplies **no reproducible peak RPS, latency distribution, hardware inventory or failure-test dataset**. Our inference: copying that stack cannot establish Gujarat capacity. The diagram's `UIDAI DB` and deletion shorthand do not authorize direct UIDAI access or destructive case deletion. [NeGD case study and linked architecture](https://negd.gov.in/isl/Directory/statedata/95)

Implementation consequence: retain stable identity, separate verification decisions, durable integration events and a controlled-hosting route. Require measured load/restore evidence before statewide claims. Preserve the [previously retained official diagram](frontend-research/up-flow.jpeg) as research evidence and keep newly authored project diagrams separate in [graphs](graphs/README.md).

## 2. Decision register

| Decision | Choice and evidence | Consequence / remaining gate |
|---|---|---|
| ADR-01 — delivery shape | A React/TypeScript frontend and FastAPI modular backend, rather than many independently deployed domain services at the first local-demo stage. This is an engineering choice, not a government mandate. FastAPI documents independent deployment concerns including startup, restarts, replication, memory and prerequisite tasks. [Deployment concepts](https://fastapi.tiangolo.com/deployment/concepts/) | Domain modules and explicit API contracts preserve extraction options. A single app replica is not high availability. |
| ADR-02 — database | PostgreSQL with SQLAlchemy and versioned Alembic migrations. Family/person/membership and state-machine transactions require relational integrity. PostgreSQL supports primary, foreign, unique and exclusion constraints. [Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) | Put critical uniqueness at the DB boundary, not only in frontend validation. Never make phone number a unique person/family key. |
| ADR-03 — durable workflows | Commit a domain change and an outbox record in one PostgreSQL transaction. Worker claims bounded pending work. PostgreSQL explains that `SKIP LOCKED` is useful for queue-like consumers but gives an inconsistent view inappropriate for general reads. [SELECT locking clause](https://www.postgresql.org/docs/current/sql-select.html) | Design **at-least-once** delivery with deduplicating consumers, retries and recovery. Do not advertise exactly-once delivery to external systems. |
| ADR-04 — concurrency | Serialize high-impact approval/membership changes using row locks; use an explicit revision for stale-edit rejection. PostgreSQL documents row locking and deadlock handling; SQLAlchemy's version counters apply during ORM flush, not unrestricted bulk updates. [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html), [SQLAlchemy versioning](https://docs.sqlalchemy.org/en/20/orm/versioning.html) | Lock related objects in stable identifier order, keep transactions short and retry only appropriate transient conflicts. Bulk jobs need their own concurrency invariants. |
| ADR-05 — authorization | Deny by default; check role, object ownership, assignment/jurisdiction and purpose server-side on each operation. A hidden frontend button is not a control. [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) | Residents cannot query another family's case by changing its ID. Family representatives do not automatically gain all adults' restricted benefits. |
| ADR-06 — sessions and provider boundary | Residents use Family ID/registered mobile → OTP; staff have separate credentials. `IDENTITY_PROVIDER=simulated` delivers only test challenges through the backend, not hard-coded frontend success. Server-verifiable sessions, protected cookies, CSRF and logout apply in both modes. [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) | Production requires an approved provider implementation, assurance/alternate-access policy, staff MFA and TLS. An unavailable approved adapter fails closed, never falls back to simulation. |
| ADR-07 — controlled hosting | Container images, Nginx, API/worker and PostgreSQL run on the local machine or controlled server. Database readiness and migrations precede application readiness. Compose can use dependency health/completion conditions. [Docker startup ordering](https://docs.docker.com/compose/how-tos/startup-order/) | No required hosted database, SaaS or public runtime CDN. Build-time package downloads and optional outbound official links are distinct from production data flows. |
| ADR-08 — identity boundaries | Application reference, permanent Family ID, person ID and PDS alias remain distinct. The SRS's UP observations inform routing, not Gujarat identifier policy. [UP district notice](https://ghaziabad.nic.in/%E0%A4%AB%E0%A5%88%E0%A4%AE%E0%A4%BF%E0%A4%B2%E0%A5%80-%E0%A4%86%E0%A4%880%E0%A4%A1%E0%A5%800-%E0%A4%8F%E0%A4%95-%E0%A4%AA%E0%A4%B0%E0%A4%BF%E0%A4%B5%E0%A4%BE%E0%A4%B0-%E0%A4%8F%E0%A4%95-%E0%A4%AA/) | Demo-issued identifiers are visibly synthetic and not official identity credentials. No inferred caste, citizenship, ration entitlement or payment right. |
| ADR-09 — source integration | Simulate PDS matching and scheme reports with labeled fixtures; no real government credentials or undocumented private API calls. UP's specific permissions cannot be transferred to Gujarat. [NeGD](https://negd.gov.in/isl/Directory/statedata/95) | Real PDS, Aadhaar, DigiLocker, SMS, certificates and payments remain disabled until each owner approves and tests its contract. A useful demo need not impersonate those approvals. |
| ADR-10 — scale progression | Start with indexed normalized core tables. Assess time partitioning for large audit, event and benefit histories after measurements; do not shard people by mutable district. PostgreSQL describes both benefits and limitations of partitioning, including restrictions on globally unique keys. [Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) | A future partitioning migration needs measured query plans, retention rules and explicit cross-partition uniqueness handling. No automatic claim that partitioning increases every query's performance. |
| ADR-11 — availability and recovery | Separate tested local persistence from proposed production replication/PITR. PostgreSQL supports standby replication and WAL-based point-in-time recovery. [Warm standby](https://www.postgresql.org/docs/current/warm-standby.html), [Continuous archiving](https://www.postgresql.org/docs/current/continuous-archiving.html) | Replica lag, fencing/failover, independent backups and restore drills are required. Replication alone is not backup and does not protect against every logical mistake. |
| ADR-12 — web quality | Preserve Gujarati/English, accessible semantics and the researched restrained palette. GIGW is the public-service baseline; full WCAG 2.2 AA remains the product acceptance target, not an automatically earned certification. [GIGW](https://guidelines.india.gov.in/introduction/), [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | Automated browser tests do not replace human assistive-technology and Gujarati-language validation before public launch. |
| ADR-13 — district reference freshness | The official Vav-Tharad portal states it was carved from Banaskantha on **2 October 2025**, becoming Gujarat's **34th district**. Rechecked directly for this implementation. [Vav-Tharad district administration](https://vavtharad.nic.in/) | Do not freeze an old 33-district frontend dropdown. Serve the supported reference list from the backend; full production hierarchy still needs approved LGD/department codes, boundary versions and update ownership. |

## 3. Demo policy choices, explicitly not inferred Gujarat law

- A resident can start a synthetic non-PDS registration without Aadhaar, caste or bank account. Fields not justified by the demo are not collected.
- A synthetic PDS fixture demonstrates authorized match/prefill; a wrong, missing or unknown ration reference remains a recoverable review scenario.
- The selected reviewer workflow separates recorded verification from final approval. Case-state transitions create audit/history records; permanent ID is not issued just by saving a draft.
- The authenticated applicant controls the demo application and its resulting family summary. This is **not** a complete real-world guardianship or inter-adult authorization model.
- Scheme cards and fixtures are informational demonstrations. Synthetic referrals/reported benefits do not create payments or imply a live Gujarat integration.
- Test user creation, credentials and OTP `123456` remain guarded by simulated-provider mode and are not production identity assurance. Testing helpers are secondary/collapsed, not the main public sign-in page.
- The code, tests and [implementation coverage](IMPLEMENTATION_COVERAGE.md) determine which flows are executable. A diagram or endpoint proposal alone is not implementation evidence.

## 4. Production policy and evidence still required

Government approval of the project name/work is recorded as user-provided context. It does not resolve the SRS's family definition, exact evidence alternatives, legal basis, source-owner agreements, resident representation, retention, official fees/timelines, authorized branding assets, service contacts, per-scheme decision powers or statewide SLOs. Synthetic demos proceed with explicit conservative boundaries. Real-data production requires these controls; the software must not silently default to broader authority.

Source access limitations from the earlier research remain in its source register. The missing Excalidraw attachment was not rediscovered during implementation. Primary technical documents are living documentation; lock actual package/image versions in the dependency manifests and recheck vendor/security support at deployment, rather than interpreting this research date as a permanent version guarantee.

The local PostgreSQL container uses the 17 series; [17-series constraints](https://www.postgresql.org/docs/17/ddl-constraints.html) and [17-series locking SELECT](https://www.postgresql.org/docs/17/sql-select.html) were also checked. The cited integrity/queue patterns are not dependent on newly added PostgreSQL 18-only functionality.
